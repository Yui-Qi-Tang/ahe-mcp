## 要回答的問題

在來源已正確擷取的前提下，寫入者先查既有證據、比對適用條件，並保留未解決問題，能否讓下一個讀者更清楚回答：**目前知道什麼、哪裡互相不相容、哪裡尚未檢查，以及哪些變更仍未完成？**

Issue 18 組另外從「歷史上已接納的錯誤主張或錯標來源」開始，觀察新查證到達後能否如實表達現況。這些歷史缺陷是刻意設定的初始條件；新比對仍由外部正確完成，不把本輪改成擷取器準確率測試。

本實驗承接 [狀態與決策評估方法](STATE_DECISION_EVALUATION.md)。先驗證狀態能否交接，不以修補輪數、工具次數或入庫成功率代替目標。既有 [34 輪回看](E4B_STATE_RECONSTRUCTION_20261012.md) 提供觀察背景，不是本實驗的對照組，也不回填它當時沒有的比對紀錄。

## 固定邊界

- **AHE 保存與回傳證據及既有原生狀態。** 語意比對、候選關係、可讀交接卡由外部流程產生；外部判斷不冒充 Core 的認定。
- **來源保存、主張接納、關係檢查分開。** 「寫入前」指 canonical 接納／關係決定之前。原始來源可以先完整保存，候選可以保持 pending；不能因為尚待比對就丟掉原文。
- **接納不代表相容或真實。** 兩份各自有來源支持的主張可以都被接納，同時保留外部判定的未解決衝突。發現衝突不授權自動撤回、合併或選定真值。
- **本輪先假設外部語意判斷正確。** 使用預先覆核的合成案例判斷表，驗證查詢、記錄及交接；這不能證明模型會正確識別衝突。外部模型擔任寫入者是後續另一輪實驗。
- **不改產品契約。** 使用現有查詢及審閱接納流程。標準 MCP 尚未開放 contradiction writer；本版不建立原生 `contradicts` 邊，也不以 SQL 或舊 profile 繞過。

一般 Query 不會自動對全部證據進行 SAT。現有一致性檢查需要外部正規化、明確 scope、watch 與 worker，詳見 [產品契約](CONSISTENCY.md)。本版不啟動 solver；三份共同矛盾的案例由外部比較流程處理，不宣稱測到原生 SAT 能力。

未來執行也必須從本 worktree 的固定來源建置並核對 binary／schema／role policy；不能使用另一分支的 binary、`internal/evidenceuse`、新 Query 宣告標籤或遷移，亦不能把那套未完成邏輯複製進實驗控制器當作「外部比對」。執行前保存檔案 hash 與工具清單，任何基準變更另開實驗版本。

## 兩組怎麼比較

| 項目 | A：依來源接納 | B：先查詢與比對 |
| --- | --- | --- |
| 原始資料 | 相同合成來源、版本、時間、適用條件與到達次序 | 相同 |
| 接納規則與決定 | 依凍結的來源審閱決定執行 | 相同，不因比對結果偷偷改政策 |
| 接納前查詢 | 不增加本次比較流程 | 查現有主張、原文、現行性及可用關係 |
| 外部比對紀錄 | 明示「本流程未執行」 | 記錄查到的候選、比較依據、結論及限制 |
| 衝突未解決 | 保留原始證據；不虛構關係檢查結果 | 另保存可查的未解決事件及後續狀態 |
| 接手者看到的內容 | AHE 查回的證據及同格式狀態卡 | 同樣內容，另有本組外部比對紀錄 |

每個故事、每組各自建立隔離的非生產 PG；**同一故事的事件之間保留同一 DB**，才能觀察累積與修正。不同組不共用 DB、回覆或比對歷史。測試審閱使用明示的 `TEST APPROVAL STUB`，只模擬預先固定的合成案例決定；若聲稱 AHE 操作通過，仍須有實際 MCP 呼叫與原生收據。

兩組的來源內容、canonical 主張及已授權原生生命週期變更應可按案例身份對照；本版不做去重刪除。若不同，先列流程偏差，不能把差異歸因於比對紀錄。B 額外查詢、文字與耗時正是干預的一部分，全部記錄。本實驗比較兩種寫入／交接流程，不估計 AHE 相對普通檔案庫的獨立優勢，也不拆分檢索、篇幅與說明各自的效果。

Issue 18 組同樣遵守此對照：兩組取得相同原始查證材料及既定審閱決定，只有 B 另作比對和整理。外部「此用途先不要使用」紀錄不改寫 AHE 的 admission，也不讓 B 偷偷少接納一份來源。本版不執行消費端過濾或寫回防線，故不能把紀錄存在算成已阻止使用。

## B 組每次寫入的固定順序

1. **保存新來源與候選。** 保留原始 bytes、來源身份、revision、精確引用、到達時間；區分來源所述的有效時間。記錄 pending／admitted 等實際狀態。
2. **界定比較對象。** 外部給出「對象、屬性、版本、條件／時間」及身份未知處。SWE 類觀測另綁原始版本、候選補丁、測試與環境；不同補丁一成一敗不是自動矛盾。
3. **先查既有事實。** 依固定身份／範圍查候選，再取正文、來源及現行性。不能只看摘要、最高排名或同字命中；比較範圍須包含可能的支持、反證與共同約束。保留查詢、分頁、實際回覆及讀取失敗。
4. **外部逐項比對。** 對可比較的候選記錄重複、補充／支持、適用條件不同、候選取代、可能衝突或仍不能判定；同一資料可與不同舊資料具有不同關係。三方共同不相容不能強塞成兩兩衝突。
5. **保存比對收據，再執行原審閱流程。** 收據綁定精確來源、候選及已讀版本。原生接納結果另存；比對完成不等於接納獲准。測項中的 fresh-v2 取代維持新主張 pending，依現有專用 reviewer 契約完成，不能先普通接納再假裝完成取代。
6. **查回並發布當時狀態。** 核對接納／取代是否真的生效、比較所依據的資料是否仍匹配，列出未解決問題。新資料插入比較窗口、權限或範圍變動時，舊結果標「需重查」，不能沿用成最新結論。

執行版須先凍結每個故事的查詢選擇規則、scope、分頁／容量限制與正文讀取規則。預期答案中的「哪幾份衝突」只供評估，不可直接當成檢索候選名單。比較器只能評估實際取回且範圍允許的內容；沒取回的條件不能由案例答案偷偷補入。

查無結果只代表這次查詢未命中。截斷、讀取失敗、權限遮蔽或範圍未完成時，記「檢查不完整」，不寫「沒有衝突」。若 API 沒有跨呼叫的同一快照保證，就保存各次版本與查回指紋，明列競態窗口；不把外部重查說成 Core 提供原子性的全庫檢查。

## 未解決時要留下什麼

本版採用**外部追加式比對紀錄＋AHE 原生收據引用**。紀錄和狀態卡屬於實驗流程；標明是否已交付讀者。不得寫成「AHE 原生查詢已自動包含這些判斷」。現有 `core-records` 可保存外部 checks／representations，但 opaque 紀錄不會自動變成衝突邊或一致性 watch；本版先不增加這個儲存變因。

| 可讀欄位 | 保存內容 |
| --- | --- |
| 這次檢查什麼 | 事件身份、比較範圍、對象／版本／條件、檢查者及判斷規則版本 |
| 比對了哪些資料 | 全部實際讀取的候選、精確 ID／版本／引用、查詢及分頁收據；未讀成功者另列 |
| 哪些說法不能一起成立 | 兩份或多份來源、各自主張、共同適用條件、外部判斷理由；只有懷疑時明寫不確定 |
| 哪些地方沒查完 | 身份未知、必要條件缺失、範圍／權限限制、工具錯誤；不得用空清單暗示完整 |
| Core 實際做了什麼 | 每個參與者的 source、candidate 與 canonical 身份對應，pending／admitted、原生取代等操作的收據與查回結果；外部候選關係另列 |
| 現在還差什麼 | 未解決原因、需要哪類新證據／審閱決定、下一步及待處理者；不知道就記未知 |
| 後續如何更正 | 指向前一紀錄與新的來源／決定／收據，保留變更前後及時間，不覆寫原判斷 |
| 結論還適用嗎 | 對應的讀取版本／範圍、查回時間、目前匹配或需重查；不宣稱永久有效 |

紀錄採三個分開的狀態欄，避免一個「完成」掩蓋問題：

- **檢查進度：** 未檢查／不完整／完成指定範圍／需重查。
- **外部比較結果：** 未發現不相容／發現不相容／尚不能判定；均附適用範圍。
- **問題處理：** 未解決／等待補件或決定／已有處理憑據／經覆核撤銷原判斷。沒有問題紀錄時標不適用。

「完成指定範圍」不是全庫一致；「已有處理憑據」須列明原因。例如專用取代已成功且查回確認，僅代表舊版退出該次現行判斷，不證明新版為真。若外部比較標錯，新增更正紀錄並保留原錯誤；不能為維持舊結論硬撤回來源。

結論必須綁定完整參與集合：對甲乙、乙丙分別查無矛盾，不能寫成甲乙丙一起相容。接納失敗後，比對紀錄仍可描述「既有證據與 pending 候選的不相容」，但不能描述成兩個 canonical 節點的衝突。

**沒有後續更新，未解決狀態就保持。** 再次讀取、再次成功接納、時間經過或有人寫「已處理」，都不能單獨關閉問題。參與資料已變更但尚未重查時，保留歷史衝突並顯示目前適用性未知。

示例狀態卡應能用一般文字讀懂：

> 同一服務、同一設定版本與時段，來源甲記錄「允許寫入」，來源乙記錄「禁止寫入」。兩份主張均已按來源審閱接納。外部比較認為兩者不能同時描述同一狀態；目前沒有足以排除任一方的證據，問題仍未解決。未建立原生衝突邊。需要核對設定來源與有效時間；此次檢查只涵蓋列出的來源與版本。

卡片後面連到兩份原文、查詢及接納收據和比對紀錄；不用讀完整 JSON 才知道發生什麼事。

先做 **11 個短故事，每個 3 個觀察點，每組 33 份狀態卡，兩組共 66 份**。觀察點為：新資料前、新資料處理後、後續事件或明確無操作後。下列是案例規格，尚非已執行的測試。

這 11 個基礎故事維持原定義；下節新增 6 個 Issue 18 故事，分組計分。合計 **17 個故事、每組 51 卡、兩組 102 卡**，不能把新增案例當成舊實驗結果。

| 故事 | 新資料與第三觀察點 | 要能分清楚的狀態 |
| --- | --- | --- |
| 1. 重複說法 | 另一來源說同一版本的 timeout 為 30 秒；後續再讀 | 重複／支持不等於新增獨立證實，更不能自動刪原文 |
| 2. 互補條件 | 補上 timeout 適用於哪種操作；後續再讀 | 多了條件，不誤標為衝突或取代 |
| 3. 同條件相反 | 相同服務、版本、時段同時有允許／禁止寫入；後續無人處理 | 兩份已接納且外部問題仍未解決；不能查一次就消失 |
| 4. 不同條件的結果 | 候選補丁甲成功、乙失敗；第三次補齊各自環境資料 | 不把不同候選的測試結果誤當同命題矛盾 |
| 5. 明確取代 | 新版到達但尚 pending；第三點完成已授權 fresh-v2 取代並查回 | 到達順序、外部取代意圖與原生已生效取代不同 |
| 6. 身份／時間缺件 | 表面相反但其中一份未提供有效時段；第三點補件確認時段不同 | 先不能判定，再縮小原疑義；保留舊判斷，不回填成早就知道 |
| 7. 結論因變動失效 | 對已檢查來源完成取代；第三點仍未重做外部比較 | 原紀錄只描述歷史，當前結果需重查；不假裝已解除或仍確定衝突 |
| 8. 查詢未完整 | 相關資料在下一頁但讀取失敗；第三點恢復讀取並完成比對 | 第一份結果是不完整，恢復後才能報該範圍的結論 |
| 9. 三份共同矛盾 | 已有「至少一扇門開著」「甲門關著」，再加入「乙門關著」；後續無操作 | 三份合起來不相容、任兩份可相容；保留整組及未解決狀態 |
| 10. 比對後又有寫入 | 在讀取與發布之間，用另一 client 加入相關相反資料；第三點重查 | 舊比較不能覆蓋未讀的新資料；記錄競態與重查結果 |
| 11. 比對完但接納失敗 | 候選與既有主張被判不相容，但原生審閱 subject 已過期而拒絕接納；第三點依新審閱完成預定測試決定 | 外部問題仍有紀錄，候選卻未成 canonical；完成後才更新參與者身份與實際狀態 |

第三個故事的服務條件與第九個故事的門集合須在 fixture 中精確限定，不能用省略前提製造假衝突。第十個故事只驗證預先指定的交錯次序，不宣稱排除所有 race。每個故事的完整來源、事件次序、查詢邊界、判斷表及預期原生操作須在執行前逐項覆核並凍結。

| --- | --- | --- | --- |

| 13. 一句話混入另一檔案的行為 | 主張以檔案甲為來源，卻同時描述甲與乙 → 核對甲與乙，分別形成有來源的候選 → 在契約允許時，以同物件 fresh-v2 將原主張縮限到甲，另獨立接納乙的更正 | 哪一部分被哪份來源支持、哪一部分錯誤；原生取代若真的完成就如實列出，乙的更正對照仍只是外部關聯；既有衍生父項未自動換掉 | 對無法用既有取代處理的舊主張提供撤回；若要讓更正對照或矛盾成為原生關係，須有各自的審閱契約與讀回 |
| 14. 摘要被錯標為逐字摘錄 | 合成的失真引文已宣告 `verbatim/exact_excerpt`，兩主張共用它 → 與可取得的同版本原文比較，確認差異 → 再查兩個相依主張及同為 `unknown` 的另一份無關來源 | 原宣告與後來發現分列；來源問題沿精確 snapshot 綁定連到兩個主張，其中一句正確也不能消除來源問題；無關來源不受牽連 | 來源層級的獨立審閱／更正事件與 Query 投影，連到所有真正綁定該 snapshot 的主張；不能只撤回某一句或修改舊 metadata |
| 15. 主張查對了，舊來源仍不可靠 | 舊紀錄有來源疑義且歷史 provider revision 不可取得 → 今日原文支持該主張 → 取得有固定版本、可核對的材料並另行審閱新紀錄 | 今日支持、歷史對應無法查證、舊來源疑義分開；新舊紀錄保留各自來源，不自動變成取代、等價、兩份獨立佐證或替換推導父項 | 既有新來源接納可沿用，但原生來源評估／時效投影及按用途檢查仍缺；新 admission 或再次宣告 verbatim 本身不是來源修復 |
| 16. 錯誤依據被推導包起來 | 建立完整 AND 父項鏈，末端依據均已接納 → 外部查出其中一個祖先不宜作當前依據 → 接到仍選用該鏈的候選行動與明示依據清單 | 從行動一路追到問題祖先，列明用途與未解決原因；不能因末端 admitted 或候選附有「SAT」說法而消除疑義；有效替代方案須有自己的完整依據 | 同一快照的完整治理／祖先狀態，以及消費端用途政策；要求現行依據的寫回通道還需接受當下的共同檢查，不能只驗父項曾被接納 |
| 17. 舊查證通過後，狀態又變了 | 保存有範圍的外部查證通過紀錄，另一讀者已取得舊版本 → 新增有明確決定的外部排除或來源問題紀錄 → 舊讀者再次提出使用 | 原查證對原輸入仍是歷史結果；外部排除／來源疑義另列且不能被舊 PASS 自動清除，當前用途需重查；不宣稱已撤回或已有防 race 保證 | 治理變動進入 Query／view／cache 身份；原生審閱修正與現行依據寫回之間的交易檢查。外部重查不能消除查完到提交之間的窗口 |

第 14 個故事另有固定的同版本原文，因此可以驗明確錯標；第 15 個故事沒有歷史原文，必須保持歷史比較未知，不能用今日原文倒推。第 16 個故事涵蓋原回報的 SAT 風險，但本版只檢查候選明示依據的交接，不啟動 planner／solver，也不將候選聲稱 SAT 算成實際求解結果或寫回阻擋證明。

舊缺陷的 seed 必須標示為刻意建構的合成負例與 `TEST APPROVAL STUB`。可以保留錯誤主張／宣告來測治理缺口，但不能以此宣稱來源真的逐字、主張已驗真，或代替真實人的決定。只使用本基準允許的標準入口；如無法建立所需原生狀態，就保留建立失敗與該案例，列為「原生前置未建立」，不可用 SQL、舊 profile、另一分支程式或假收據補成已接納。外部模擬卡可另供文件檢視，不能計入原生實跑成績。

狀態表達的主要成績也必須來自實際 Query 與本組外部紀錄。只依 fixture 編出的卡，另列「文件示例」，不能算外部表達實跑通過；受阻觀察點仍留在原分母，逐點列出未驗原因。已完成的觀察點可以獨立核對，不能替後續受阻點補成通過。

### 外部能先做什麼，產品要補什麼

| --- | --- | --- |

本版外部紀錄新增三類，彼此不能互相清除：**主張排除決定、來源比較發現、限定範圍的查證報告**。至少保存非機密 store 身份、主張 ID／指紋或 source snapshot ID／保留內容 hash、原宣告、比較材料及版本、判準與用途、結果／未知／限制、決定或查證者、時間、修訂鏈。更正參照可以省略，也可以跨物件；它不自動改 Core 關係或祖先。

來源檢查再分「保留 bytes 是否一致」「與指定 provider 版本是否對應／覆蓋」「主張是否得到所檢材料支持」。保留 hash 相同不能代替 provider 原文核對；主張支持通過也不能清除已記錄的來源問題。若歷史欄位缺失就記缺失，不製造版本、審閱身份或核准收據。

精確連到來源或祖先，只證明關聯存在，不代表問題效力相同。每項發現另列種類、涉及的片段／主張、適用用途及未判定範圍；「來源宣告有誤」「某主張不受支持」「特定用途排除」不能互換。第 14、16 個故事須保留未受該判斷涵蓋的主張或用途作對照，不能沿 snapshot 或 AND 鏈一律判假、一律停用。

### 三種結果各自交代

1. **外部狀態表達：** 是否能讀出疑義、依據、作用範圍、待處理事項，以及「原生尚未生效」。這是本版 Issue 18 組的主要評估。
2. **現有原生契約：** 實際標準工具呼叫、審閱、接納、拒絕和查回各自留收據。跨物件取代被有界拒絕，可以是該契約符合預期；不等於舊主張已被停用。缺工具、前置失敗、未執行均具名列出。
3. **待產品補能力：** 撤回／恢復、來源更正、治理投影、標準矛盾 writer、用途檢查及交易防線分項列「未實作於本基準／本輪未驗」。外部紀錄通過不能將這欄改成 PASS，缺能力也不能從案例分母刪掉。

原生能力之後若補齊，須從完成驗證的產品版本另建對照，才能測「原生決定已生效、查回一致、消費端與寫回真的阻擋」。本版不藉故擴張到 AHE 自行判斷自然語言真偽，或自動修正／合併全部證據。

## 如何評估「更清楚」

每份狀態卡用相同六個問題檢查；答案必須能指回具體材料：

1. 正在描述哪個對象、版本、候選和時間／條件？
2. 哪些是當時的來源主張與觀測，各自的根據是什麼？
3. 有哪些不相容、相容或不能判定的關係，適用範圍是什麼？
4. 哪些資料／檢查仍缺少，和單純未讀到有何不同？
5. 哪些只是外部建議，哪些已由原生操作實際生效，哪些問題未解決？
6. 本次結論對應哪個資料版本；當下仍匹配、需重查，還是不知道？

| 量測 | 分母與判定 | 不能偷換成 |
| --- | --- | --- |
| 狀態可還原 | 基礎組每組 33 卡 × 6 題＝198 格；Issue 18 組每組 18 卡 × 6 題＝108 格。合計每組 51 卡／306 格，分組列正確且有據、部分、錯誤、缺失與六題全對卡數 | 檔案存在率或「寫了很多紀錄」；混合兩種案例後只報一個高分 |
| 未解決／未知是否可見 | 凍結判斷表中應為未解決、不能判定、不完整、需重查的觀察點，各列分子／分母；同時列誤報衝突／不必要停手 | 只要求常常回答「有衝突」，或把所有問題一律標未知 |
| 比對能否追溯 | B 每次預定比對事件均列查詢、候選、原文、判斷、實際操作和更正鏈完整／部分／缺失；A 列未執行 | 引用匹配等於語意正確，或 A 缺少 B 特有欄位就算 A 狀態回答錯誤 |

答案鍵分成「共同來源所描述的狀態」及「各組當時實際完成的檢查／操作」。A 如實回答「流程尚未比對」是正確的流程描述，不能因為沒有 B 的紀錄就算錯；但也不能把它當成已回答來源之間的相容性。反過來，B 有判斷表不代表相容性已由 Core 證明。逐題分開列描述正確性與所需資訊是否齊全，不以單一高分混在一起。

若接手者直接從原文指出衝突，兩組都接受有據答案，但標為接手者本次的外部判斷，不能回填成寫入時已檢查。來源本就不足時，正確界定未知才算有據；已可判定卻只寫未知則列資訊不足，和錯誤陳述分開。工具錯誤或缺卡仍留在原分母，另外標出基礎設施原因。成本另記查詢數、讀取量、保存量與耗時；本版沒有模型 token 或修補成功率成績。

先由主代理做收據和凍結判斷表的機械核對，再準備不知道案例答案的**人類接手覆核**：用相同格式、隱去組名的卡片與可查原文回答六題，記錄所需查閱及疑點。避免同一覆核者先看一組答案再替另一組作答；兩組交錯分配，不把相依觀察點當獨立樣本。資料內容可能透露組別，故只稱遮蔽標籤，不稱完全盲測。尚未完成這一步時，只能報資料鏈是否齊全，不能宣稱別人已能接手；不擅自啟用答題／評分子代理。

判準先固定：B 若比 A 多出六題全對的卡，且沒有新增錯誤狀態主張，可報本案例集的交接改善。若只是附件更完整、答案沒有改善，就只報追溯改善。**任何把未解決說成已解決、把外部關係說成原生已建立、把不完整／過期檢查說成當前一致的輸出，都列為未達成狀態契約。** 不能用總分提升掩蓋這些錯誤。

Issue 18 組另外核對：外部排除是否誤報成原生撤回、來源發現是否誤當所有主張為假、歷史查證是否被當當前許可、跨物件更正是否被誤報為取代。兩組都可以如實回答「產品尚無此能力」而得到狀態描述正確；產品能力覆蓋仍須另列未完成，不能合成一個「Issue 18 已解決」分數。

## 執行次序與保留資料

1. **案例與契約凍結：** 完成 11 個基礎 fixture＋6 個 Issue 18 fixture、六題預期答案（共同來源與各組流程分開）、來源範圍、查詢規則與工具 schema 映射。Issue 18 原生前置、外部可驗項及產品缺口分開列。記錄固定 checkout／HEAD、dirty 差異、schema／role policy、依賴與內容 hash，確認沒有另一分支的程式或 binary；本計畫不把規劃時版本冒充執行版本。
2. **隔離環境預檢：** 確認非生產 DB 所有權、各 profile 的實際工具、現行性及 fresh-v2 必要操作。缺能力就明列阻斷，不切換 legacy、不擴充 Core 補成 PASS。
3. **逐事件實跑：** 兩組交錯執行、保存所有入出參、原生收據、讀回結果與外部紀錄。凍結後不能看到結果就改判斷表、補查或選擇性重跑；修正需另開版本且保留失敗。
4. **狀態交接評估：** 逐格核對並準備人類覆核；保留與預期不符、無法判定及流程偏差，分開報外部判斷、記錄／交付和 Core 行為。
5. **決定是否進下一輪：** 若此條件下仍交代不清，就先定位缺了什麼。若能交代清楚，再規劃由 E4B 自己查詢與比對的實驗，檢驗它是否按流程做、關係是否判對、是否因此少做無據重試；本版不預先宣稱這些收益。

原始執行資料保留在獨立的私有 Product 驗證目錄，按「故事／組／事件」保存來源、查詢、比較、審閱、操作、查回、狀態卡與評分；不混入既有 34 輪資料。公開報告只放方法、合成例子及可核對的彙總，區分 AHE 原生資料與外部附加紀錄。

執行前確認兩項原訂前置限制：第 8 題的現行 list 工具沒有下一頁／cursor／offset 契約；第 11 題尚無可用標準操作讓同一 pending 候選的不可變 subject 自然過期。各保留兩個後續觀察點為前置阻斷，不改成擴大 limit、偽造 subject 或 SQL 修改來算通過。第 11 題是本案例建立方法尚未具備，不能據此宣稱審閱保護失效。
